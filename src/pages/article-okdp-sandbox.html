Installer OKDP en local avec Kind, Flux et KuboCD

Le sandbox officiel d'OKDP, étape par étape : ce que fait chaque commande, dans quel ordre attendre, et les quatre points où l'installation cale le plus souvent.

OKDP 10 novembre 2026 · Par l'équipe Kubotal · 7 min de lecture

En bref : le sandbox OKDP s'installe en cinq étapes sur un cluster Kind : créer le cluster, installer Flux, installer KuboCD, appliquer les contrats, les contextes et les releases, puis régler le DNS et le certificat. Il faut 16 Go de RAM et 4 CPU. On obtient les fondations de la plateforme et le Control Plane ; les services Data se créent ensuite par projet.

Cet article suit le README du dépôt okdp-sandbox tel qu'il était le 10 novembre 2026. Les commandes viennent de ce dépôt ; les explications sont les nôtres. Si une commande diffère, le README fait foi : il évolue avec les versions. Pour situer le projet avant de commencer, lisez notre guide d'OKDP.

Que faut-il avant de commencer ?

  • Machine : 16 Go de RAM et 4 CPU au minimum.
  • Conteneurs : Docker ou Podman, avec au moins 8 Go de RAM et 2 CPU alloués.
  • Outils : Kind, kubectl et la CLI Flux.
  • Réseau : un accès aux registres de conteneurs, directement ou par un proxy.

La mémoire allouée au moteur de conteneurs est le premier point à vérifier. Sur un poste où Docker Desktop garde son réglage par défaut, le cluster démarre mais les pods restent en attente faute de ressources.

Étape 1 : comment créer le cluster Kind ?

Le cluster tient en un seul nœud. Sa configuration publie trois ports de la machine vers le cluster : 80 et 443 pour le trafic web, et un port UDP pour le serveur DNS local.

git clone https://github.com/OKDP/okdp-sandbox.git
cd okdp-sandbox

cat > /tmp/okdp-sandbox-config.yaml <<EOF
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: okdp-sandbox
nodes:
- role: control-plane
  extraPortMappings:
  - containerPort: 30080
    hostPort: 80
  - containerPort: 30443
    hostPort: 443
  - containerPort: 30053
    hostPort: 30053
    protocol: UDP
EOF

kind create cluster --config /tmp/okdp-sandbox-config.yaml

Les ports 80 et 443 doivent être libres sur le poste. Un serveur web local ou un autre cluster Kind qui les occupe fait échouer la création.

Étape 2 : pourquoi installer Flux sans dépôt Git ?

Flux est le moteur GitOps : il réconcilie en continu l'état du cluster avec un état décrit. Dans le sandbox, il n'est relié à aucun dépôt Git. Les manifestes sont appliqués à la main avec kubectl, et Flux sert seulement à exécuter ce que KuboCD lui demande.

flux install

kubectl -n flux-system wait --for=condition=Available deploy \
  -l app.kubernetes.io/part-of=flux --timeout=300s

Derrière un proxy d'entreprise, il faut transmettre les variables HTTPS_PROXY, HTTP_PROXY et NO_PROXY aux contrôleurs Flux avant de continuer. Le README donne la commande. Sans elle, Flux ne peut pas télécharger les packages et tout reste bloqué plus loin, sans erreur évidente.

Étape 3 : que fait KuboCD dans l'installation ?

KuboCD est la couche de livraison continue posée sur Flux. Il transforme une ressource courte, la Release, en ressources Flux complètes. C'est lui qui déploie tous les composants d'OKDP. Son fonctionnement est détaillé dans notre analyse de KuboCD.

kubectl apply -f clusters/sandbox/flux/kubocd.yaml

kubectl -n flux-system wait --for=condition=Ready \
  helmrelease/kubocd-controller --timeout=300s

kubectl wait --for=condition=Established --timeout=300s \
  crd/contexts.kubocd.kubotal.io \
  crd/releases.kubocd.kubotal.io \
  crd/configs.kubocd.kubotal.io \
  crd/clustercontracts.kubocd.kubotal.io \
  crd/connections.kubocd.kubotal.io

kubectl -n kubocd wait --for=condition=Available \
  deploy/kubocd-ctrl-controller --timeout=300s

Les trois attentes ne sont pas décoratives. Appliquer les releases avant que les CRD soient enregistrées produit une erreur « no matches for kind » ; les appliquer avant que le contrôleur tourne les laisse sans effet.

Le README installe ensuite metrics-server, avec un correctif : le délai par défaut des sondes, une seconde, est trop court pour un cluster Kind à un seul nœud. Sous charge, le pod redémarre en boucle. Appliquez le correctif tel qu'il est fourni.

Étape 4 : dans quel ordre déployer la plateforme ?

Trois familles de ressources s'appliquent dans un ordre précis. Leur logique est expliquée dans l'article sur les packages, releases et connexions d'OKDP.

OrdreRessourceRôle
1 Contrats (ClusterContract) Les types de connexion que les composants peuvent publier ou consommer.
2 Contextes (Context) La configuration partagée : domaine d'ingress, classes de stockage, émetteur de certificats, paramètres OIDC.
3 Releases (Release) Ce qui est installé, avec quelle version de package et quels paramètres. 
kubectl apply -f clusters/sandbox/contracts/
kubectl apply --server-side -f clusters/sandbox/contexts/
kubectl apply -f clusters/sandbox/releases/

kubectl get releases -A --watch

Le déploiement prend plusieurs minutes : les releases passent à l'état READY l'une après l'autre, selon leurs dépendances. Pour bloquer jusqu'à la fin au lieu de surveiller :

kubectl wait --for=jsonpath='{.status.phase}'=READY release --all \
  -n kubocd-system --timeout=900s

À ce stade, le cluster contient Keycloak, CloudNativePG et une instance PostgreSQL, External Secrets, le Spark Operator, cert-manager, ingress-nginx et le Control Plane d'OKDP.

Étape 5 : comment accéder aux services ?

Les services sont exposés sous le domaine okdp.sandbox. Deux réglages restent à faire sur le poste.

  • DNS : soit un serveur DNS local, recommandé parce qu'il couvre tous les services d'un coup, soit des entrées dans /etc/hosts, à tenir à jour à la main. Le guide docs/dns-configuration.md du dépôt détaille chaque système.
  • Certificat : le sandbox utilise une autorité de certification locale. Soit vous l'exportez et l'importez dans le magasin de confiance, soit vous acceptez les avertissements du navigateur.
kubectl get secret default-issuer -n cert-manager \
  -o jsonpath='{.data.ca\.crt}' | base64 -d > okdp-sandbox-ca.crt

La console s'ouvre alors sur https://okdp-ui.okdp.sandbox. L'authentification passe par Keycloak, avec le compte par défaut indiqué dans le README. Ce compte est public : il convient à un poste local, jamais à un environnement partagé.

Quels sont les quatre pièges les plus fréquents ?

  • Le certificat Keycloak non accepté. Si vous choisissez d'ignorer les avertissements, ouvrez d'abord Keycloak et acceptez son certificat. Tant que ce n'est pas fait, la console et les autres services ne peuvent pas dialoguer avec lui et la connexion échoue.
  • Le domaine changé à moitié. Si okdp.sandbox est interdit par votre politique réseau, il faut modifier le suffixe d'ingress et les cinq adresses OIDC du contexte. Changer le suffixe seul déplace Keycloak, mais les services continuent de valider les jetons sur l'ancien hôte.
  • Le proxy oublié côté services. Le proxy se règle deux fois : sur les contrôleurs Flux, puis dans le contexte de la plateforme pour les services qui téléchargent des jeux de données.
  • La suppression d'une release protégée. Un webhook refuse de supprimer les releases marquées comme protégées, par exemple cert-manager. C'est voulu. Pour passer outre en connaissance de cause, il faut d'abord mettre spec.protected: false sur la release.

Et après : comment obtenir Spark, Trino et Superset ?

Les services Data ne font pas partie de l'installation. Ils se créent par projet, depuis la console ou avec kubectl. Le dépôt fournit un projet de démonstration complet : un espace de noms, ses secrets, son PostgreSQL, ses connexions et ses services.

Ce projet demande d'abord le composant de stockage objet, optionnel dans le sandbox : SeaweedFS, ou tout service compatible S3. Le troisième niveau charge ensuite un exemple de lakehouse en trois couches, bronze, silver et gold, avec ses notebooks et ses DAG Airflow.

Ce découpage en projets est le cœur du modèle d'OKDP. Nous l'expliquons dans l'article sur l'architecture et le Control Plane.

Comment tout supprimer ?

kind delete cluster --name okdp-sandbox
rm /tmp/okdp-sandbox-config.yaml

Supprimer le cluster suffit : rien n'est installé en dehors, à part le certificat que vous auriez importé dans votre magasin de confiance.

Du sandbox à la production : le sandbox prouve que la plateforme fonctionne, pas qu'elle est dimensionnée. Stockage, haute disponibilité, annuaire d'entreprise et sauvegardes restent à concevoir. C'est le travail que Kubotal mène en phase de cadrage.
