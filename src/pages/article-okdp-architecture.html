Architecture d'OKDP : le rôle du Control Plane

Deux couches, des projets modélisés comme de simples espaces de noms, et un serveur qui ne génère aucun manifeste lui-même. Ce que ces choix impliquent pour une équipe plateforme.

OKDP 10 novembre 2026 · Par l'équipe Kubotal · 6 min de lecture

En bref : OKDP sépare un catalogue de moteurs Data, utilisables seuls, et un Control Plane qui les instancie par projet. Le Control Plane est un serveur d'API et une console web. Il ne déploie rien directement : il lit un catalogue dans un Context KuboCD et crée des Release KuboCD. Un projet est un espace de noms Kubernetes, sans CRD ni opérateur supplémentaire.

La page d'accueil d'okdp.io présente l'architecture en deux blocs. Cet article ouvre ces blocs à partir des dépôts publics du projet, lus le 10 novembre 2026. Pour une vue d'ensemble, commencez par notre guide d'OKDP.

Quelles sont les deux couches d'OKDP ?

CoucheContenuDépendance
Plateforme Data Spark et son opérateur, Hive Metastore, Trino, Superset, Airflow, JupyterHub, Polaris. Aucune envers le Control Plane : chaque composant se déploie seul.
Control Plane Un serveur d'API et une console web pour déployer, configurer et suivre les composants. Kubernetes et KuboCD.

La première couche est un assemblage, pas une réécriture. Trino et Airflow sont déployés avec leurs charts d'origine. OKDP ajoute son propre travail là où l'intégration manquait : des images Spark, un filtre d'authentification OIDC pour les interfaces Spark, un proxy pour suivre les applications en cours depuis le Spark History Server, un chart pour Hive Metastore.

Conséquence pratique : vos traitements ne dépendent pas d'OKDP. Un job Spark ou un DAG Airflow écrit pour la plateforme reste un job Spark ou un DAG Airflow.

Que fait exactement le Control Plane ?

La console web est une application exécutée dans le navigateur. Elle n'a ni identifiants de cluster ni logique côté serveur. Elle ne peut donc pas piloter Kubernetes seule.

Le serveur du Control Plane est son pendant : un service écrit en Go, déployé dans le cluster, qui traduit les actions de la console en opérations. Il crée les espaces de noms des projets, déploie et met à jour les services, sert le catalogue, et diffuse l'état des services, des pods et des métriques. Les identifiants et la logique métier restent côté serveur.

  • Interfaces : une API REST, et des événements envoyés par le serveur (SSE) pour le suivi en direct.
  • Authentification : OIDC et TLS sont assurés par l'ingress de la plateforme, placé devant le serveur, et non par le serveur lui-même.
  • Droits : le chart Helm lui attribue un compte de service limité à ce dont il a besoin, à savoir gérer des espaces de noms et lire ou écrire les ressources KuboCD.

Pourquoi le serveur ne génère-t-il aucun manifeste ?

C'est le choix d'architecture le plus structurant. Le serveur ne fabrique pas de YAML Kubernetes. Il fait deux choses :

  • il lit le catalogue de services dans une ressource KuboCD Context ;
  • il crée des ressources KuboCD Release, une par service à déployer.

KuboCD, déjà utilisé pour installer la plateforme, fait le reste : il résout la configuration, produit les ressources Flux et Flux applique les charts. Le serveur réutilise le moteur GitOps en place au lieu d'en dupliquer la logique.

Deux bénéfices en découlent. D'abord, ce que la console déploie et ce qu'un administrateur déploie avec kubectl passent par le même chemin et donnent le même résultat. Ensuite, tout ce que fait la console est visible dans le cluster sous forme de ressources lisibles :

kubectl get releases -A
kubectl -n okdp-system get context platform -o yaml

Une console qui masquerait ses actions derrière une base interne serait plus simple à écrire, et beaucoup plus difficile à auditer.

Pourquoi un projet est-il un simple espace de noms ?

OKDP modélise un projet comme un espace de noms Kubernetes. Aucune CRD « Project », aucun opérateur dédié. Les services d'un projet sont des Release qui portent une étiquette de projet.

Ce choix a un coût et un bénéfice. Le coût : le modèle de projet est limité à ce qu'un espace de noms sait exprimer. Le bénéfice : tous les mécanismes Kubernetes existants s'appliquent sans adaptation. Quotas de ressources, politiques réseau, RBAC et outils d'observabilité fonctionnent déjà par espace de noms.

Un projet complet, tel que le sandbox le montre, empile cinq éléments dans cet ordre :

  • l'espace de noms ;
  • les secrets du projet ;
  • un PostgreSQL dédié, avec une base par service qui en a besoin ;
  • les connexions, qui décrivent où joindre les bases et le stockage objet ;
  • les services Data eux-mêmes.

Chaque projet a donc ses propres bases et ses propres instances de services. L'isolation ne repose pas sur des droits dans un service partagé, mais sur des instances séparées.

D'où vient la configuration commune ?

Du Context. C'est une couche de configuration déclarative et partagée : suffixe d'ingress, classes de stockage, émetteur de certificats, catalogues, paramètres d'authentification. KuboCD injecte ces valeurs dans chaque composant au déploiement.

Quand un contexte change, seuls les composants concernés sont réconciliés. On peut superposer plusieurs contextes : un contexte d'organisation pour les valeurs par défaut, puis un contexte par environnement qui les complète ou les remplace.

Un détail mérite l'attention si vous installez le Control Plane sur votre propre cluster. Les releases créées par le serveur ne citent aucun contexte explicitement : elles prennent ceux que la ressource Config de KuboCD déclare par défaut. Si le contexte de la plateforme n'y figure pas, les packages sont rendus avec une configuration vide.

apiVersion: kubocd.kubotal.io/v1alpha1
kind: Config
spec:
  defaultContexts:
    - name: platform
      namespace: okdp-system

Comment l'identité est-elle gérée ?

Tous les services s'authentifient en OIDC auprès d'un même fournisseur, dont les adresses sont lues dans le contexte. Le sandbox utilise Keycloak.

OKDP prend aussi en charge KubAuth, proposé comme composant optionnel. La différence est concrète : KubAuth stocke les utilisateurs, les groupes et les clients OIDC comme des ressources Kubernetes. C'est ce qui permet au Control Plane de les gérer depuis la console. Avec Keycloak seul, la rubrique Identité de la console est masquée : c'est un état normal, pas une panne.

Installer KubAuth ne bascule pas la plateforme. La bascule est une décision séparée, qui modifie le contexte et fait réconcilier tous les services sur le nouveau fournisseur. Elle se prépare.

Que retenir pour une équipe plateforme ?

  • Vous pouvez adopter par étapes. Les moteurs d'abord, avec Helm ; le Control Plane quand plusieurs équipes arrivent.
  • Le cluster reste lisible. Projets, services et configuration sont des ressources Kubernetes ordinaires.
  • KuboCD est une dépendance réelle. Le Control Plane ne fonctionne pas sans lui. Il faut le comprendre avant d'exploiter la plateforme : voir comment OKDP est packagé avec KuboCD.
  • Le coût suit le nombre de projets. Des instances par projet isolent bien, et consomment plus qu'un service mutualisé. Le dimensionnement se fait projet par projet.

Pour voir ces mécanismes tourner, le plus rapide reste d'installer le sandbox en local.
