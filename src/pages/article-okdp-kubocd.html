OKDP et KuboCD : packages, releases et connexions

Comment une plateforme de plus d'une dizaine de composants se livre sous forme d'artefacts OCI versionnés, et comment ses services se trouvent les uns les autres sans adresse codée en dur.

OKDP 10 novembre 2026 · Par l'équipe Kubotal · 5 min de lecture

En bref : chaque composant d'OKDP est un Package KuboCD : un artefact OCI versionné qui embarque un descripteur et un ou plusieurs charts Helm. Une Release dit quel package installer et avec quels paramètres. Un Context fournit la configuration commune. Une Connection relie deux services par un contrat typé, par exemple s3 ou trino. Les packages et leur déploiement vivent dans deux dépôts distincts.

Cet article décrit le packaging d'OKDP à partir des dépôts platform-packages et okdp-sandbox, lus le 10 novembre 2026. KuboCD est le projet de livraison continue porté par Kubotal ; si vous le découvrez, lisez d'abord KuboCD : déployer sur Kubernetes sans maîtriser Helm.

Pourquoi ne pas livrer OKDP avec Helm seul ?

Une plateforme Data n'est pas un chart, c'est un ensemble de charts qui doivent s'accorder. Superset a besoin d'une base PostgreSQL et d'un client OIDC. Trino a besoin d'un métastore et d'un stockage objet. Spark a besoin du même stockage et du même métastore.

Avec Helm seul, cet accord se règle dans des fichiers values.yaml : la même adresse de base, le même domaine, le même émetteur de certificats recopiés d'un fichier à l'autre. Chaque recopie est une occasion d'erreur, et chaque nouvel environnement multiplie les fichiers.

KuboCD répond à ce problème par quatre objets.

Quels sont les quatre objets à connaître ?

ObjetCe qu'il estQui le maintient dans OKDP
Package Un artefact OCI versionné : un descripteur d'application et un ou plusieurs charts Helm. Le dépôt platform-packages.
Release L'instruction d'installer un package, avec sa version et ses paramètres. Le dépôt de déploiement, ou le Control Plane.
Context La configuration partagée, injectée dans tous les composants. Le dépôt de déploiement.
Connection Un point d'accès typé, identifié par un contrat. Publiée par un package, consommée par un autre.

Que contient le dépôt des packages ?

Le dépôt platform-packages ne fait qu'une chose : définir, construire et publier les packages. Il ne contient aucune release, aucun contexte, aucune amorce Flux.

packages/
├── system/
│   ├── okdp-control-plane-server/
│   └── okdp-control-plane-ui/
└── services/
    ├── airflow/
    ├── hive-metastore/
    ├── jupyterhub/
    ├── okdp-examples/
    ├── polaris/
    ├── spark-defaults/
    ├── spark-history-server/
    ├── spark-operator/
    ├── spark-rbac/
    ├── superset/
    └── trino/

Deux familles : les packages système, qui forment le Control Plane, et les packages de services. Les dépendances tierces et d'amorçage sont emballées dans un autre dépôt, sandbox-dependencies : OKDP distingue ce qu'il maintient de ce qu'il se contente d'intégrer.

Un package se construit avec une commande :

kubocd package ./packages/services/superset/superset.yaml \
  --ociRepoPrefix quay.io/okdp/platform-packages

Le résultat est poussé sous la forme {préfixe}/{nom}:{tag}. Changer le préfixe suffit à publier dans le registre interne d'une organisation, ce qui compte pour les environnements sans accès à Internet.

Pourquoi séparer les packages de leur déploiement ?

Le dépôt okdp-sandbox est le miroir du précédent : il ne construit aucun package, il déploie ceux qui sont publiés. On y trouve l'amorce du contrôleur KuboCD, les contrats, les contextes et les releases.

Cette séparation correspond à deux métiers et à deux rythmes. Publier une nouvelle version de Superset est un travail de packaging, validé par une intégration continue qui construit tous les packages. Décider qu'un cluster passe à cette version est une décision d'exploitation, qui tient en une ligne modifiée dans une release.

Pour votre organisation, la conséquence est simple : vous n'avez pas à dupliquer le dépôt des packages. Vous écrivez votre propre dépôt de déploiement, avec vos contextes et vos releases, et vous consommez les packages publiés.

À quoi servent les Connections ?

C'est la partie la moins visible et la plus utile. Une Connection est un point d'accès typé par un contrat. Les packages d'OKDP utilisent cinq contrats :

  • s3, pour le stockage objet ;
  • database-server, pour un serveur de bases de données ;
  • hive, pour le métastore ;
  • iceberg-catalog, pour un catalogue Iceberg ;
  • trino, pour le moteur SQL.

Un package publie une connexion dans ses sorties et un autre la consomme par un paramètre de référence. Trino ne reçoit pas l'adresse du métastore : il reçoit une référence vers une connexion de type hive.

L'intérêt apparaît au premier remplacement. Le sandbox utilise SeaweedFS comme stockage objet, mais tout service compatible S3 convient. Passer à un autre stockage revient à fournir une autre connexion de contrat s3 ; les services qui la consomment ne changent pas. Le contrat joue le rôle d'une interface.

C'est pour cela que les contrats s'appliquent en premier lors d'une installation, avant les contextes et les releases : ils définissent le vocabulaire que tout le reste utilise.

Qu'est-ce que cela change à l'exploitation ?

  • Une montée de version est un changement de tag. Les releases existantes se mettent à jour en place, sans suppression.
  • L'état se lit d'une commande. kubectl get releases -A liste tous les composants avec leur phase.
  • Les composants critiques sont protégés. Un webhook refuse la suppression d'une release protégée, par exemple cert-manager, tant que la protection n'est pas levée explicitement.
  • Un changement de contexte se propage seul. Seuls les composants concernés sont réconciliés.

La contrepartie est réelle. KuboCD est une couche de plus à comprendre, au-dessus de Flux et de Helm. Quand un déploiement échoue, le diagnostic traverse trois niveaux : la release, les ressources Flux qu'elle a produites, puis le chart. Une équipe qui exploite OKDP doit savoir lire les trois.

Par où commencer ?

Lisez une release du sandbox, puis le package qu'elle référence : en dix minutes, le modèle devient concret. Ensuite, installez le sandbox en local pour voir les releases passer à l'état prêt. L'article sur l'architecture et le Control Plane montre enfin comment la console s'appuie sur ces mêmes objets.

Besoin d'un dépôt de déploiement pour votre organisation ? Contextes par environnement, registre interne, intégration à votre annuaire : c'est le cœur de nos missions de build sur OKDP.
