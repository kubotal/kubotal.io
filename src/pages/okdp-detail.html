OKDP : la plateforme Data open source sur Kubernetes

Ce qu'est l'Open Kubernetes Data Platform, comment elle est construite, comment l'essayer, et ce que Kubotal y apporte en tant que contributeur du projet.

OKDP Mis à jour le 10 novembre 2026 · Par l'équipe Kubotal

En bref : OKDP (Open Kubernetes Data Platform) est une plateforme de données 100 % open source, sous licence Apache 2.0, qui s'exécute sur Kubernetes. Elle assemble des moteurs reconnus (Spark, Trino, Airflow, Superset, JupyterHub) et un Control Plane qui les instancie par projet. Kubotal contribue au code d'OKDP et accompagne les équipes qui veulent l'évaluer, le déployer et l'opérer.

Qu'est-ce qu'OKDP ?

OKDP est une plateforme de services de gestion de données composée de logiciels open source conteneurisés, exécutés sur une infrastructure Kubernetes. Elle couvre le cycle de vie de la donnée : collecte, stockage, traitement, analyse et exposition. Sa conception est modulaire : une équipe peut déployer l'ensemble ou seulement les composants dont elle a besoin.

Le projet a été lancé en 2024. Il a été initié par la DGFiP, rejoint par Orange et d'autres organisations, au sein de l'association TOSIT (The Open Source I Trust). Le site officiel est okdp.io et le code est publié dans l'organisation OKDP sur GitHub.

Comment OKDP est-il architecturé ?

L'architecture repose sur deux couches. Les distinguer évite l'erreur la plus fréquente à l'évaluation : croire qu'il faut tout adopter d'un bloc.

CoucheRôleCe qu'elle contient
Modules Data & IA Un catalogue de moteurs open source, utilisables seuls ou combinés, sans dépendre du Control Plane. Spark, Trino, Hive Metastore, Airflow, JupyterHub, Superset, Spark History Server.
Control Plane La couche d'automatisation : portail, API, isolation par projet, quotas, authentification OIDC, secrets, observabilité. Un serveur d'API, une console web et un catalogue de services instanciés projet par projet.

Dans la pratique, la plateforme pose d'abord des fondations partagées : Keycloak pour l'identité, CloudNativePG pour PostgreSQL, External Secrets pour les secrets, le Spark Operator pour les traitements, cert-manager et ingress-nginx pour le TLS et le routage. Les services Data ne sont pas installés une fois pour tous : le Control Plane les crée pour chaque projet, avec ses propres ressources et ses propres accès.

Ce découpage a une conséquence directe sur le dimensionnement. Le coût fixe est celui des fondations et du Control Plane ; le coût variable suit le nombre de projets et les services que chacun active.

Comment OKDP est-il déployé ?

Le déploiement de référence est GitOps. Flux applique l'état décrit dans Git, et KuboCD emballe chaque composant dans un package OCI exposé par une ressource Release courte. Un cluster OKDP se lit donc comme une liste de releases, chacune avec sa version et ses paramètres, et non comme un empilement de fichiers values.yaml.

KuboCD est le projet de livraison continue porté par Kubotal. Ses ressources Kubernetes appartiennent au groupe d'API kubocd.kubotal.io, visible dans la documentation du sandbox OKDP. Pour comprendre ce mécanisme avant d'ouvrir le dépôt, lisez notre analyse de KuboCD, Helm et Flux.

Les composants restent aussi installables un par un avec Helm, pour les équipes qui ne veulent qu'une brique. Le dépôt helm-handbook documente cette voie.

Comment essayer OKDP sur un poste ?

Le dépôt okdp-sandbox déploie la plateforme sur un cluster Kubernetes local créé avec Kind. C'est le chemin le plus court pour juger le projet sur pièces.

  • Machine : 16 Go de RAM et 4 CPU au minimum, dont au moins 8 Go et 2 CPU alloués à Docker ou Podman.
  • Outils : Docker ou un runtime compatible, Kind, kubectl et la CLI Flux.
  • Résultat : les fondations et le Control Plane. Les services Data sont ensuite créés par projet depuis le Control Plane.
git clone https://github.com/OKDP/okdp-sandbox.git
cd okdp-sandbox
# puis suivre le « Quick start » du README : cluster Kind, Flux, releases KuboCD

Le sandbox se lit en trois niveaux : la plateforme, un projet de démonstration complet, puis des exemples de traitements qui alimentent un lakehouse en couches. Chaque niveau est optionnel et s'appuie sur le précédent. Suivez le README officiel pour les commandes exactes : elles évoluent avec les versions.

Quand choisir OKDP, et quand s'en passer ?

OKDP convient quand trois conditions sont réunies : l'organisation exploite déjà Kubernetes ou a décidé de le faire, elle veut garder la maîtrise de son infrastructure et de ses données, et plusieurs équipes doivent partager une même plateforme avec une isolation par projet.

  • Souveraineté : le cluster reste le vôtre, sur site ou chez le fournisseur de votre choix, et aucun composant n'est sous licence propriétaire.
  • Réversibilité : les moteurs sont des projets open source standards. Les traitements Spark, les requêtes Trino et les DAG Airflow ne dépendent pas d'OKDP pour s'exécuter ailleurs.
  • Coût : il n'y a pas de licence. Le budget se déplace vers l'infrastructure et vers les compétences d'exploitation.

OKDP n'est pas le bon choix dans deux cas. Une équipe sans compétence Kubernetes et sans intention d'en acquérir paiera l'exploitation plus cher qu'un service managé. Et un besoin centré sur l'ingestion temps réel ou le service de modèles de langage devra composer avec la feuille de route : ces domaines y figurent comme des évolutions à venir, à vérifier sur la roadmap officielle.

Quel est le rôle de Kubotal dans OKDP ?

Kubotal contribue au code d'OKDP. Les chiffres ci-dessous viennent des pages publiques de contributeurs GitHub, relevées le 10 novembre 2026, en comptant les comptes dont le profil indique Kubotal.

Dépôt OKDPCe qu'il portePlace des contributeurs Kubotal

okdp-control-plane-server L'API du Control Plane. 1er et 2e contributeurs.

S'y ajoute KuboCD, le moteur de déploiement utilisé par le sandbox. Cette position nous donne une connaissance du projet que la documentation seule ne transmet pas : les choix d'architecture, leurs raisons, et les points qui demandent de l'attention en production.

OKDP reste un projet communautaire, hébergé par TOSIT et ouvert à tous. Kubotal n'en est ni le propriétaire ni l'éditeur.

Comment Kubotal accompagne un projet OKDP ?

  • Cadrage : vérifier qu'OKDP répond au besoin, choisir les modules, dimensionner le cluster et chiffrer l'exploitation.
  • Build : déployer la plateforme en GitOps, la raccorder à l'annuaire, au stockage objet et à l'observabilité existants.
  • Run : opérer les montées de version, la sécurité et la capacité.
  • Transfert : former l'équipe interne pour qu'elle exploite la plateforme sans nous.

Le détail de ces modes est décrit sur la page Accompagnement, et nos domaines d'intervention sur la page Expertise.
